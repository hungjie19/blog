<KeyTakeaways>
  <p>為什麼讓 LLM 照著既有 tag 清單挑，選出來的總是 #AI、#LLM 這種泛詞？因為 tag 治理要求先看清單，模型會被錨定，直接挑最安全的詞，不再從內容推理；解法是把順序反過來，先讓 LLM 只看內容自由推理 tag，再把同一概念的不同寫法收斂成既有標籤；這是我在 Obsidian vault 與 Astro 部落格實際改過的流程。</p>
</KeyTakeaways>

有一天我想找自己寫過的一篇 Obsidian 文章。那時部落格還沒有站內搜尋，只能點 tag 找，我直覺它一定在 `#Obsidian` 底下，點進去卻找不到。

我最在意的其實是部落格的 tag，因為它是公開的。不過〈[Obsidian Tag 越長越亂：用 Controlled Vocabulary 收斂標籤](/posts/obsidian-tag-controlled-vocabulary/)〉講過，summary 的 tag 是產生部落格 tag 的依據之一，所以 tag 治理一直是上下游一起修。只是問題通常會先在部落格這端被發現：找某篇文章的 source 時，或文章發布後想翻出來給別人看時。

回頭看上游的 summary，也有類似的問題：我越來越常看到同一批 tag，`#AI`、`#LLM`、`#Agent`、`#Workflow`。這些詞套在哪篇都說得通，但跟那篇文章到底在講什麼，幾乎沒有關係。

這兩個問題，都是那套規則用了一陣子之後冒出來的。

## Obsidian 那篇為什麼沒有 `#Obsidian`？

那篇〈[Obsidian MCPVault](/posts/obsidian-mcp-knowledge-search/)〉掛的是 `AI`、`MCP`、`Knowledge-Management`、`Markdown`。內文提到 Obsidian 23 次，主角的 tag 卻不在上面，反而有一個 `AI`。

它的 tag 是照當時的規則挑的：先看全部既有 tag，有接近的就重用，每篇 3–5 個。名額很少，既有的泛詞又永遠「接近」，於是 `AI` 先佔掉一格，主角就被擠出去了。規則裡也沒有一條說「文章主角是某個產品，就一定要掛它」。

我請 LLM 重新掃一遍部落格全部文章的 tag。我的要求是：之前規則太僵化，文章應該要有更多不同的 tag；但相似的 tag 還是要用同一個，因為之前修的就是同一個概念出現中文、英文、近似拼法好幾個版本。

逐篇掃下來，Obsidian 只是其中一篇。講 Orca 的文章沒有 `Orca`，講 Cloudflare Workers 短網址的文章沒有 `Cloudflare`，標題寫著 Spokenly 的文章沒有 `Spokenly`。

規則改成兩條：

- 描述性 tag 上限從 3–5 個放寬到 **3–7 個**。
- **文章主角是具名產品時一定要掛，就算全站只有這一篇也一樣**，audit 也不因為只有一篇就把它淘汰。

這次重掃補了 88 篇文章的 tag，tag 從 105 個變成將近 150 個，Obsidian 那篇也補上了 `Obsidian`。

不過上限和主角規則只是讓該掛的有位置掛。更根本的問題是挑 tag 的順序，這在 summary 那邊看得更清楚。

## summary 的 tag 為什麼總是 `#AI`、`#LLM`？

有一次我在寫 session summary，LLM 照規則先回報「先讀 tag 規則」。看到這行，我把醞釀一陣子的不滿丟出來：

> 「我認為應該 llm 先根據文章推倒 tag 後寫完文章在用 obsidian get all tags 驗證是否有相似 改過去 只是要不相似重複出現就好，因為現在這做法可能誤殺了 tag 的多樣性？」

當時 vault 的規則是篇 1 定下來的：寫 tag 前先呼叫 `list_all_tags` 拿到全部既有 tag，再跟候選詞比對，「有同義、近義、大小寫、單複數、粒度相近的既有 tag 就重用，真的沒有才新增」。vault 那時已經有 600 多個 tag。

我的懷疑很直接：一次拿到幾百個 tag，LLM 就懶得從內容想了，直接從清單裡挑一個說得通的。

LLM 同意，而且拿同一個 session 剛寫好的 summary 當證據。那篇講的是 Markdown endpoint 和 GitHub alerts 語法遷移，先看過清單才挑 tag，結果掛的是 `plugin`、`migration`、`frontmatter`。這些詞在清單裡都有，也都勉強相關，但只看內容的話，該寫的是 `markdown-endpoint`、`github-alerts`、`remark`、`content-negotiation`，而這幾個詞在清單裡根本沒有同義詞。

這在心理學叫 anchoring（錨定效應）：先看到的資訊會拉住後面的判斷。泛詞又特別容易被選中，因為它們永遠不會錯。這個 vault 幾乎每篇都跟 AI 有關，`ai` 掛在哪篇都說得通，也正因為如此，它分不出任何一篇。Obsidian 那篇的 `AI` 擠掉 `Obsidian`，也是同一件事。

再往下看規則的措辭，真正的閘門有兩句：

- **「如果答案不是明確的『是』，不要新增」**：預設不新增，舉證責任全壓在新詞身上。
- **「粒度相近就重用」**：具體的詞很容易被認定跟某個泛詞「粒度相近」，然後被吞掉。

這跟篇 1 廢掉的高頻詞表是同一個病：給模型一份清單，它就往清單裡挑。之前廢掉的是「至少挑 2 個」的 quota 和高頻詞表，這次的清單藏在流程的第一步，所以前兩次修法都沒抓到。

## 先自由推理，再收斂：不同就是不同

當初「先看清單」要擋的是同義詞重複，這個需求還在。所以不是拿掉比對，而是把比對移到後面：

1. **先推理**：只看內容，寫出最貼切的 tag，這一步不看任何清單。
2. **再收斂**：用 `list_all_tags` 逐一檢查候選詞。
   - 同一個概念、只是寫法不同（大小寫、單複數、連字號、已登記的同義詞）→ 換成既有 tag。
   - 相關但不同的概念，或比既有 tag 更具體的子概念 → 保留新詞。
3. **新詞變多不用擔心**：總量交給低頻的 audit 收斂。寫入時只負責不製造同義重複。

關鍵在第 2 步的界線：**只合併同一個概念，不合併相關的概念**。如果收斂時退回「挑一個接近的舊詞」，就又回到原點了。

規則的措辭也一起翻過來：「新 tag 門檻」從「不是明確的是就不新增」改成「清單裡沒有同一個概念的 tag 就新增」，並寫明「相關不等於同一個」；「粒度相近」從合併條件裡拿掉。

拿剛才那篇 summary 照新流程重跑一次：

| 舊 tags（先看清單再挑） | 新 tags（先推理、再收斂） |
|---|---|
| `aeo`、`astro`、`cloudflare` | `aeo`、`astro`、`cloudflare`（比對後沿用） |
| `frontmatter`、`plugin`、`migration` | `content-negotiation`、`markdown-endpoint`、`github-alerts`、`remark`（新增） |

比對時有一個值得記的判斷：清單裡已經有 `rehype`，但 `remark` 是 Markdown 處理流程的另一個階段，兩者相關但不同，所以保留新詞。照舊規則的「粒度相近就重用」，`remark` 很可能就被吞進 `rehype` 了。

LLM 也主動說明這次重跑不完美：它在 context 裡已經看過那份清單，不算真正從零開始推理，真正的效果要等之後新的 session 才看得出來。我那時的回答是「我知道我覺得是沒錯」，方向本身我不需要等實測才確定。

這套順序 vault 和部落格兩邊都改了。部落格的 `to-blog` skill 有自己的 tag 規則，一樣改成先推理、再收斂，只合併同一個概念；建立新 tag 規則用的範本也一起改，免得之後新建的 repo 又長回舊流程。

## 改完一個月：泛詞消失了

寫這篇時，我回頭掃了一次 vault 的 summary，數 `ai`、`llm`、`workflow`、`agent`、`tools`、`setup` 這類泛詞出現幾次：

| 期間 | summary 篇數 | 泛詞出現次數 |
|---|---|---|
| 改之前 | 222 | 19 |
| 改之後 | 47 | 0 |

改之後的 47 篇，掛的是 `orca`、`cloudflare-d1`、`click-analytics`、`oklch` 這種一看就知道在講什麼的詞。改之前那批檔案中間經過幾次 audit，被清掉過一些泛詞，所以 19 這個數字只能當參考；但改之後一次都沒出現，至少說明新流程沒有讓泛詞回來。

這跟我自己的感受一致。最近文章的 tag 推理都滿準的，真的會出現很特殊的 tag，畢竟每次遇到的問題都不一樣。檢查文章時，我花在檢查 tag 上的次數也變少了。

## 心得

tag 治理雖然能防止 tag 繼續發散，但它反而限縮了 LLM 的推理能力。所以我把整件事反過來：先讓 LLM 推理，再跟它講現在有哪些 tag。這樣既能保持關鍵詞的靈活度，也能收斂相同的關鍵詞。推理和收斂兩件事都還在，只是換了一個方向。

我覺得這是比較好的方式，而不是把關鍵詞整個收斂到一個非常狹窄的範圍裡。
