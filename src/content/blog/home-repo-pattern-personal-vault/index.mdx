<KeyTakeaways>
  <p>Home Repo Pattern 是什麼？用一個有版控的 repo 放 skills、AGENTS.md 與共用文件，再用一 repo 一行的指標連到其他專案，讓 Agent 從這裡看得到全貌；這是我用個人 Obsidian vault 對照的結果，我沒有照文章讓每個 session 都從 home 出發，公司專案也另外處理。</p>
</KeyTakeaways>

最近 Matt Pocock 在 AI Hero 發表的 [The Home Repo Pattern](https://www.aihero.dev/the-home-repo-pattern) 很快就在討論圈爆開，他還錄了一支 YouTube 影片 [The Home Repo: The effortless multi-repo agent setup](https://www.youtube.com/watch?v=hWe-j78vNpc)。我印象很深的是作者自己的說法：他原本以為這個觀念大家都有，所以一直沒講，直到在 X 上發文、討論熱烈起來，才決定寫成文章。

我讀完的第一個反應是：這不就是我現在的 Obsidian vault 嗎？

所以這篇不是「照著文章重建一套」，而是拿文章當對照表，看看我原本的做法哪裡已經到位、哪裡其實還沒做完整。

## 原文在說什麼：一個 repo 當家，其他 repo 用指標連過去

文章要解決的問題很直接：Agent 在某個 repo 裡啟動，就只看得到那個 repo。每個 repo 各自複製一份 skills 和 Agent 設定，要規劃一個跨 repo 的功能時，Agent 手上永遠缺一塊拼圖。

它的答案是 Home Repo，定義只有一句：

> A Home Repo is one repository that holds your skills, your AGENTS.md and your shared docs.
>
> （Home Repo 是一個 repository，放你的 skills、你的 AGENTS.md 和共用文件。）

幾個重點：

- **Agent 從這裡啟動**：文章寫的是「You run your agent in the Home Repo.」，跨 repo 的功能也在這裡討論，而不是進到某個單一 repo 裡。
- **用指標連到其他 repo**：AGENTS.md 裡有一段「Other Repos」，一個 repo 寫一行，格式是 `<name> (<what it is>): <local path>. Clone from <remote> if missing.`。Agent 要動哪個 repo，就照指標過去；本機沒有就自己 clone。指標後面還可以加提示，文章的範例是「Read its AGENTS.md before changing it.」。
- **child repo 留自己的東西**：各 repo 保留自己的 AGENTS.md、build／test 指令和程式碼，home 只放共用的部分。
- **skills 要有版控**：放在 `~/.claude/skills` 這種使用者資料夾，文章的說法是「A user folder is the stopgap until then.」，也就是過渡用的權宜做法。
- **規模**：大約 20 個 repo 用一份清單沒問題；到 400 個左右，「one pointer per repo is too many decisions for the agent」，就該改成每個領域一個指標檔。
- **跟 monorepo 的關係**：能用 monorepo 就用 monorepo；不行的時候（例如公開與私有 repo 混在一起），Home Repo 才是替代方案。

## 我原本就有類似的做法

我的 vault（`~/ai_session_summary`）一開始不是為了當 home repo 而建的，它是我存 session summary 的地方。但用久了，它長出來的樣子跟文章描述的很接近：

- **它是起點**：我習慣每次跟 AI 討論完就寫一份 [session summary](/posts/session-is-knowledge/)，這些 summary 累積成知識庫，再被提煉成部落格文章和 Slidev 簡報。
- **私人 skill 放在這裡**：寫 blog、做圖卡、wiki ingest 這些只跟 vault 工作流有關的 skill，都在 vault 的 `.claude/skills/`。
- **有版控**：整個 vault 是一個 git repo，所有變更都有歷史可以回頭查。

有趣的是，我請 AI 拿文章對照時，它第一次的回答是：我的 home 其實拆成三處，`~/.claude` 放通用設定與 skills、vault 放知識、另一個 `agent-core` 放給特定 Agent 讀的參考資料。

我看完文章的直覺不是這樣。我本來就是把 vault 當家在用，文章只是剛好印證了我的想法。回頭再對一次原文，文章其實也沒說家要是 `~/.claude`，反而是把只放在使用者資料夾的 skills 叫作 stopgap。`~/.claude` 是「在任何 repo 開 session 都會載入」的那一層，跟 home repo 不衝突，它只是我自己多加的一層。

## 真正缺的：後來新增的專案沒被納進來

對照下來，我缺的不是結構，是指標。

vault 的 `CLAUDE.md` 裡原本只寫了兩個下游 repo：`~/blog` 和 `~/my_slide`。但後來我陸續開了好幾個 side project：部落格的 three.js 島嶼頁、短網址服務、課程練習 repo、幾個本機小工具。它們都是後來新增的，我沒有回頭把它們加進 vault 的清單。結果就是 Agent 在 vault 裡根本不知道這些 repo 存在。

這裡跟文章有個差別。文章假設 Agent 都從 home 啟動，再 cd 進目標 repo；我平常不是這樣。要替某個專案加功能時，我會直接在那個專案底下開 session。所以對我來說，指標不是用來「出發」的，而是讓我在 vault 裡討論、整理資料、把 summary 轉成產出時，Agent 知道其他 repo 在哪裡、各自是做什麼的。

我把原本的「下游 Repos」改成「Other Repos」，照文章的格式一行一個，依角色分成三組。換成通用名稱大概長這樣：

```markdown
## Other Repos

這個 repo 是 home：需要動其他 repo 時照下表過去，進去後先讀該 repo 的 CLAUDE.md。

**下游**（筆記整理後輸出到這裡）：

- blog（個人部落格）：`~/blog`。Clone from `https://github.com/<you>/blog.git` if missing.
- slides（簡報）：`~/slides`。Clone from `https://github.com/<you>/slides.git` if missing.

**Side projects**：

- side-project-a（一句話說明它是什麼）：`~/side-project-a`。Clone from `https://github.com/<you>/side-project-a.git` if missing.
- local-tools（本機小工具集）：`~/local-tools`。只在本機，無 remote。

**Agent 設定**：

- agent-config（全域規則、通用 skills）：`~/.claude`。Clone from `https://github.com/<you>/agent-config.git` if missing.
```

每行的用途、remote 都是讓 AI 直接從各 repo 的 `git remote` 和它自己的 `CLAUDE.md` 開頭抓的，不是我手打。沒有 remote 的本機 repo 就標「只在本機」，Agent 才不會想去 clone 一個不存在的東西。

## 順便檢查：私人 skill 有沒有放到共用的 root？

既然要分清楚哪些東西屬於家，skill 也一起檢查。我的 skill 有三個可能的位置，各自的載入範圍不同：

| 位置 | 什麼時候載入 | 放什麼 |
|---|---|---|
| `~/.claude/skills/` | 在任何 repo 開 session 都載入 | 真正通用的 skill |
| vault 的 `.claude/skills/` | 只有在 vault 開 session 才載入 | 只跟 vault 工作流有關的 skill |
| `~/agent-core/skills/` | 不會自動載入，由特定 Agent 用絕對路徑讀 | 給特定 Agent 的參考資料 |

檢查之後確實抓到一個：寫 Threads 貼文的 skill 要讀寫 vault 裡的資料夾，卻放在 `~/.claude/skills/`，等於在每個 repo 都多載一個用不到的 skill。我把它搬回 vault，並把這三層規則寫進 vault 的 `CLAUDE.md`，下次新增 skill 的 Agent 才知道該放哪。

> [!TIP]
> ### 專案 skill「不需要就不會載入」
> 把 skill 放在 vault 而不是 `~/.claude`，代價是在其他 repo 開 session 時用不到它。但對只服務 vault 工作流的 skill 來說，這正是想要的行為：不需要的地方就不載入，也不會佔用 Agent 的注意力。

## 因為是 cd 過去，所以進專案要先讀規範

原文的工作方式是：Agent 在 Home Repo 啟動，要動哪個 repo，就照指標 cd 過去（本機沒有就 clone）。所以文章的指標範例後面特別加了一句提示：

> Payments API: ~/repos/acme/payments-api. Read its AGENTS.md before changing it.
>
> （Payments API 在 `~/repos/acme/payments-api`，改動前先讀它的 AGENTS.md。）

這句提示不是多餘的。Agent 的專案規則（`CLAUDE.md`、`AGENTS.md`）是在 session 啟動時，依起始目錄載入的；之後 cd 到別的 repo，只是工作目錄換了，那個 repo 的規則不會自動補讀。Agent 照樣能在那裡改檔，只是不知道那裡的規矩。這個機制我在 [Agent 換專案時，為什麼不一定會讀 CLAUDE.md](/posts/agent-project-instructions/) 寫過，解法是在全域規則加一條「換到別的專案時，先讀它根目錄的 `CLAUDE.md` 或 `AGENTS.md`」，就不用在每一行指標後面重複這句提示。

反過來，home 這個起點本身也要讓每個 Agent 讀得到。Claude Code 啟動時讀 `CLAUDE.md`，Codex 只會自動載入 `AGENTS.md`；home 如果只有其中一份，另一個 Agent 在 home 開 session 時就看不到 Other Repos 和其他規則，而「進專案先讀規範」那條也幫不上忙，因為起點不算換專案。原文的做法是讓另一個檔案只放一行指標：

> If my harness loads a different file, add that file as a one-line pointer to AGENTS.md.
>
> （如果你的 harness 載入的是另一個檔案，就把那個檔案寫成一行指向 AGENTS.md 的指標。）

我自己習慣更直接一點，在每個 repo 根目錄放一個 symlink，讓兩個檔名指向同一份內容：

```bash
ln -s CLAUDE.md AGENTS.md
```

兩種做法效果一樣，差別在一行指標要靠 Agent 照著去讀另一個檔案，symlink 則是兩個檔名本來就是同一份內容。之後只要改 `CLAUDE.md`，`AGENTS.md` 就跟著同步，不會出現兩份規則各自漂移。

> [!TIP]
> ### git 身分也可以寫進 home 的規則
> 如果全域 git 設定是公司身分，個人 repo 很容易不小心用公司 email commit。把「這些 repo 一律用個人身分，commit 前先確認 local 有設」寫進 home 的 `CLAUDE.md`，透過 `AGENTS.md` symlink，Claude Code 和 Codex 都會照同一條規則做。

## 為什麼沒有照抄文章的做法

文章其他的建議我也一條條看過：每個 feature 開 worktree（我已經用 Orca 在做）、讓 Agent 把 issue 開在各 repo 的 tracker（我用 vault 的 handoff 資料夾統一收）、集中一份 coding standards（我的 side project 技術棧都不一樣，沒什麼能共用）、超過 20 個 repo 要分組（我還差得遠）。這些我目前都不需要。

更根本的差別在 skill 和 Agent 的控管。照文章的做法，所有 skill 和 Agent 都收進 home、所有 session 都從 home 出發，對我來說反而會比較複雜。我目前的判斷是把「個人」和「公司」分開看：

- **個人**：vault 就是 home，side project 用指標納進來，通用的東西留在 `~/.claude`。
- **公司**：如果有前後端好幾個 repo，就挑其中一個（例如前端的 repo），把跨 repo 的指標和規則寫清楚，不跟個人的家混在一起。

## 心得

我本來就有寫 session summary 的習慣，這個習慣慢慢長成一張知識圖譜，再往外延伸到部落格、簡報，後來又多了好幾個 side project。Home Repo Pattern 給了這個狀態一個清楚的定義，讓我能更精確地把自己的 side project 都納進來管理：要討論的事、要處理的資料，都在同一個地方做，對 Agent 來說也等於一份共用記憶，少掉很多「這個 repo 在哪、是做什麼的」的來回說明。

文章講的都是很簡單的觀念，其中[「進專案要先讀規範」](/posts/agent-project-instructions/)也是我以前就踩過雷補上的。看到別人把它整理成一個有名字的 pattern，感覺蠻有趣的。不過我目前的結論是：家的定義照文章，怎麼出發照自己的習慣。至少對一個人維護十個以內 repo 的情境，這樣就夠用了。
